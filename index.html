The bill moved because the storefront does more work per visitor, not because more visitors came.

Northwind's June bill rose 38% ($3,600 → $4,970) while traffic rose 13%. The gap is not growth. It is the storefront doing more work per visitor than it should. Pages that should be served from Vercel's CDN are being rendered by functions on nearly every request, and the responses those functions produce are larger than they need to be.

That same pattern is not just a cost problem. It is the single biggest technical risk to all four of this year's commitments, because each one depends on the storefront being cacheable, secure at its API boundary, and fast enough on a phone.

2.2 Commitment 1: Hold infrastructure spend flat through the holidaysAt risk

Status: At risk. Root causes are configuration-level and addressable before peak.

What we observed

Traffic vs. compute diverged. Edge requests (the count of all requests hitting Vercel) rose 13%, from 3.7M to 4.2M. Function invocations for page renders rose far more: / +165% (to 1.8M), /product/[handle] +140% (to 950K). When compute grows 10× faster than requests, requests that were previously answered from the CDN cache are now reaching origin.

Bytes per visitor grew. Fast Data Transfer on / went from 210 GB to 620 GB against a nearly flat 1.35M → 1.4M edge requests: roughly 155 KB → 443 KB per request. /product/[handle] went 222 KB → 491 KB per request. Visitors aren't the driver; page weight is.

Live inspection confirms cache misses. /blog/[slug] returns cache-control: no-store and renders on every request (184ms TTFB). Product-page RSC responses (/product/[handle].rsc) return Cache-Control: private, no-cache, no-store, max-age=0, must-revalidate with Age: 0. Every product navigation is a fresh function invocation by instruction, not by accident of cache expiry (one observed at 637ms TTFB). The initiator chain shows heavy ?_rsc= prefetch traffic for low-priority links (/about, /shipping, /warranty).

Evidence: response headers

Functions are over-provisioned. Under Fluid compute, provisioned memory is billed while a request is in flight. Peak usage versus allocation:

Route Provisioned Peak used Ratio
/ render 1024 MB 180 MB 5.7×
/product/[handle] render 1024 MB 210 MB 4.9×
/api/orders/[id] 3009 MB 38 MB 79×
/api/revalidate 1024 MB 45 MB 23×
/api/recommendations 1769 MB 1690 MB 1.05×, at ceiling

/api/recommendations is the outlier. 950K invocations, tracking product page views 1:1. 12% of invocations are CPU-throttled, peak memory is 96% of allocation. It is called client-side on every product view and, as an API route, is not cached by default.

Image Optimization. 128K transforms (+32%). Live inspection shows thumbnails requested at w=1920 and re-encoded to AVIF from an external source on cache miss (480ms TTFB).

Middleware. 2.4M invocations, 61% on static assets (JS, CSS, images). Middleware is running where no routing or auth decision is needed.

ISR on blog. /blog shows 1,200 cache reads against 3,400 revalidation writes; /blog/[slug] averages 4,800 reads against 9,600 writes per post. Pages are being regenerated more than twice as often as they're served from the durable cache.

Why it's happening

The storefront is configured as if most of its pages were personalized, when most of them are not. The homepage, product pages, and blog are the same for every anonymous visitor and should be served from the CDN with a revalidation window. Instead:

  • no-store and dynamic rendering on public routes force a function invocation per request. (Whether this was a deliberate choice, e.g. to avoid caching cart state, or an accidental default, is to verify.)
  • Where ISR is in use (blog), the revalidation interval is too short, or on-demand revalidation is being triggered too broadly by Shopify webhooks, consistent with /api/revalidate growing 210%, likely from inventory-sync or bulk-edit tooling firing per-product webhooks. to verify Vercel's ISR documentation also notes that non-deterministic output (new Date(), Math.random()) in a page causes a write on every revalidation even when content hasn't changed.
  • /api/recommendations has no Cache-Control header, so a carousel that changes rarely is computed fresh 950K times a month, and the payload it assembles is large enough to nearly exhaust its memory allocation.
  • Memory allocations appear to have been set once at a high default and never revisited.
  • The middleware matcher isn't excluding _next/static, images, and other static paths.
  • <Image> components don't declare sizes, so the browser requests the largest candidate.

What we recommend

  1. Restore CDN caching on public routes. For /, /product/[handle], and /blog/[slug]: use ISR (export const revalidate = N) or set Cache-Control: max-age=0, s-maxage=86400, stale-while-revalidate for content that is identical for all visitors. Move any per-user element (cart count, account state) into a client component or a private route so the page shell can cache. Docs: Cache-Control headers → Recommended settings; ISR Usage and Pricing → Optimizing ISR reads and writes.
  2. Cache /api/recommendations. Add Cache-Control: s-maxage=3600, stale-while-revalidate=86400 (or move the data fetch behind Vercel's data cache). Trim the Shopify payload to the fields the carousel needs. This addresses cost, throttling, and the memory ceiling in one change. Docs: Cache-Control headers → stale-while-revalidate.
  3. Fix blog ISR. Lengthen the time-based interval (hours, not seconds) or switch to on-demand revalidation triggered only on publish. Audit the page for non-deterministic output. Use Observability+ ISR Write Utilization to confirm which pages regenerate without being read. Docs: ISR Usage and Pricing → Optimizing ISR reads and writes; KB: How to reduce ISR revalidation costs.
  4. Right-size function memory. Set allocations to roughly 2× observed peak: / and /product to 512 MB, /api/orders/[id] and /api/revalidate to 256 MB. Leave /api/recommendations alone until step 2 lands, then re-measure. Docs: Debugging slow Vercel Functions → Check function configuration.
  5. Scope the middleware matcher to exclude _next/static, _next/image, favicon.ico, and asset extensions.
  6. Declare image sizes on product and listing <Image> components (e.g. sizes="(max-width: 768px) 100vw, 33vw"), add priority only to above-the-fold images, and confirm the external image host is configured so transforms cache.
  7. Debounce /api/revalidate. If Shopify webhooks fire per-product during bulk syncs, batch them or revalidate by tag rather than by path. (Also a security item; see §2.3.)
  8. Set a Spend Management threshold and usage notifications so Finance hears about the next inflection from Vercel, not from the invoice. Docs: Manage and optimize usage → Usage alerts, notification, and spend management.

Risk if not addressed

  • Cost scales ahead of traffic. The June ratio (compute up ~10× faster than requests) applied to holiday volume produces a bill that Finance will see as a second unexplained jump, this time during the quarter that matters most.
  • /api/recommendations fails under peak. At 96% of memory and already throttling, meaningful traffic growth pushes it into errors or timeouts. That degrades every product page during the highest-intent shopping window of the year.
  • Every other commitment inherits the inefficiency. Search, mobile, and any new feature built on uncached routes and oversized payloads adds to the compute bill rather than the cache.

2.3 Commitment 2: Pass the Q1 customer-data security reviewNeeds work

Status: Needs work. The gaps are documentation and hardening, not architecture.

What we observed

For a headless Shopify storefront on Vercel, the review will concentrate on the seams Northwind owns: how the frontend authenticates to Shopify, how webhooks are verified, what functions log, and how sessions are stored. Shopify owns checkout and PCI; Vercel owns TLS, DDoS protection, and the edge; Northwind's code owns everything in between.

From the usage data and live inspection, the items a reviewer will raise:

  • /api/revalidate invocations grew 210% in a month. A revalidation endpoint reachable from the internet without HMAC verification of Shopify's X-Shopify-Hmac-Sha256 header can be triggered by anyone, which is both a cache-busting cost vector and a security finding. (Whether verification is in place is to verify; it is not visible from the outside.)
  • 3% of traffic is unverified/suspected bot. Not alarming, but with no visible bot management or rate limiting on API routes, the reviewer will ask what stops abuse of /api/*.
  • Middleware runs on 61% of static assets. Any auth or header logic in middleware is executing far more broadly than intended, which makes it harder to explain the security model cleanly.
  • no-store on public blog content suggests caching policy was set defensively rather than by data classification. A reviewer will want to see that private and no-store are applied where customer data actually flows (/account/*, /api/orders/*) and not as a blanket.
  • /api/orders/[id] is provisioned at 3 GB for a 38 MB workload. Harmless in itself, but it signals that function configuration hasn't been reviewed, and the reviewer will extend that assumption to logging and secrets.

Why it's happening

The storefront was built for launch, not audit. None of the gaps above are unusual for a headless commerce site at this stage; they are the standard set that emerges the first time someone external reads the configuration.

What we recommend

  1. Verify webhook signatures. Every Shopify webhook hitting a Vercel API route (/api/revalidate and any others) must validate X-Shopify-Hmac-Sha256 against the app secret and reject on mismatch. Log rejections.
  2. Audit secrets. Confirm Shopify Admin API tokens exist only as Vercel environment variables, scoped to production, and never reach the client bundle. Only the public Storefront API token should be browser-visible. Docs: Environment variables.
  3. Scrub PII from function logs. Review what /api/orders/[id], /account/*, and checkout-adjacent functions write to logs and any log drains (Axiom, Datadog). Names, emails, and addresses should not be logged.
  4. Set a Content Security Policy and standard security headers via next.config.js headers() or vercel.json.
  5. Harden session storage. Customer account tokens in HttpOnly, Secure, SameSite=Strict cookies; confirm no tokens in localStorage.
  6. Classify caching by data sensitivity. private, max-age=0 or no-store on /account/* and /api/orders/*; public caching everywhere else. This is the same change as §2.2 item 1, framed for the reviewer. Docs: Cache-Control headers → Personalized or per-user.
  7. Add rate limiting and bot rules on /api/* via Vercel WAF / Firewall; document them.
  8. Produce a shared-responsibility document (Shopify / Vercel / Northwind) before the review, and share Vercel's security and compliance documentation with the reviewer proactively.

Risk if not addressed

  • Review fails or is conditionally passed with remediation required before the enterprise wholesale channel opens. The channel has a date and revenue attached; a 30–60 day remediation cycle pushes both.
  • An unauthenticated revalidation endpoint is exploitable today as a cost attack (forcing regeneration) and as a way to probe the Shopify integration.
  • Discovery of the gaps during the review, rather than before it, costs Northwind credibility with the enterprise customer at exactly the wrong moment.

2.4 Commitment 3: Improve on-site product discoveryConstrained, with one immediate fix

Status: Constrained. Discovery improvements will be expensive and slow until the platform work lands.

What we observed

Search fails on ordinary queries. Live testing of the site search:

Query Result What it tells us
rain 2 results (Cascade Rain Shell, Switchback Hiking Boots) Single-word substring match works
rain gear 0 results Multi-word queries fail; the search matches the raw string, not individual words
green thermos 0 results (Granite Thermos 1L exists) No partial or attribute matching
themos 0 results No typo tolerance

The search is doing an exact substring match against the title. A shopper has to type a word that appears verbatim in a product name, spelled correctly, with no qualifiers. That is a direct, demonstrable cause of search abandonment, independent of catalog content.

Evidence: search results

Recently viewed isn't updating. to verify The "Recently viewed" rail shows the same single product across every page visited, including on product pages for other items. A discovery feature that doesn't record views isn't helping shoppers find their way back to products they considered.

Evidence: recently viewed

Search and recommendation surfaces are uncached. /search and /search/[collection] account for 310 GB of Fast Data Transfer (+63% MoM), the third-largest path. /api/recommendations (the "Related Products" carousel) is CPU-throttled on 12% of calls; on those requests the carousel arrives late or not at all.

Layout is unstable. CLS at p75 is 0.31 ("needs improvement"). LCP (2.1s) and INP (180ms) are fine. Layout shift on a commerce site typically comes from images without reserved dimensions and late-loading components, both present here (undeclared sizes, async recommendations). Shift under a shopper's finger is a direct contributor to mis-taps and abandonment.

Catalog content is thin. Product descriptions run ~70–105 characters: a single sentence, reused as the page's meta description, with no specs, fit, or care content. Even a working search index would have very little to match against.

Why it's happening

Search abandonment has three causes, in order of impact. The mechanism cause: search is a literal substring match with no tokenization, fuzzy matching, or attribute search, so most natural queries return nothing. The content cause: descriptions carry almost no searchable text, so even a good index would be matching against one sentence. The platform cause: search and recommendation surfaces are computed fresh on every interaction, making them slower and more expensive than the pages around them, and layout instability makes results harder to act on.

What we recommend

  1. Replace the search implementation. At minimum, tokenize queries and match any word against title, description, tags, and metafields; add typo tolerance. Shopify's Storefront API search (with the Search & Discovery app for synonyms and boosts) covers this without a third-party dependency; Algolia or Typesense if Northwind wants faceting and merchandising controls. This is the highest-impact discovery change available and is independent of the content work.
  2. Fix or remove Recently Viewed. Confirm whether views are being recorded (cookie, localStorage, or server-side). A discovery feature that visibly doesn't work erodes trust in the rest of the page.
  3. Cache search results. Collection pages (/search/[collection]) are the same for all visitors and should use ISR or s-maxage. Free-text search results can be cached by normalized query with a short s-maxage and stale-while-revalidate. Docs: Cache-Control headers → Semi-static.
  4. Fix recommendations first (§2.2 item 2); it is the same change and it unblocks the carousel.
  5. Reserve layout space. Set explicit width/height or aspect ratio on product images and a fixed-height skeleton for the recommendations slot. Target CLS < 0.1.
  6. Enrich the catalog (detailed below in Catalog content strategy). This is content work Northwind's merchandising team owns, and it is the single largest lever on search relevance. It is also a prerequisite for mobile (§2.5).
  7. Instrument search. Track zero-result queries, query → click, and query → add-to-cart with Vercel Web Analytics custom events, so the team can measure abandonment rather than infer it.

Catalog content strategy

Northwind's product pages carry one sentence of description (the Trailhead Canvas Jacket reads, in full, "A duck-canvas work jacket built for weather and abuse. Corduroy collar, brass hardware, blanket lining.") and reuse that sentence as the meta description. There are no materials, weights, dimensions, fit notes, temperature ranges, or care instructions anywhere on the page. Shoppers searching for "waterproof shell under 1 lb," "insulated work jacket," or "boots for wet trail" find nothing, because the words aren't in the catalog. Commercial buyers outfitting a crew, the enterprise wholesale channel, need even more: fit consistency, durability specs, and bulk sizing.

Titles: front-load what a shopper searches for

  • Structure: Product Line + Product Type + Defining Feature + Variant. Trailhead Duck Canvas Work Jacket, Blanket-Lined rather than Trailhead Canvas Jacket. Cascade 3-Layer Waterproof Rain Shell rather than Cascade Rain Shell. Summit 22L Day Pack, Hydration-Compatible rather than Summit Day Pack 22L.
  • Length: 25–150 characters, with product type and the defining feature in the first 60, since that's what survives truncation in search results and on a phone screen.
  • Format: Title Case; numerals ("22L," "3-Layer," "1L"); standard units (oz, lb, L, mm).
  • Avoid: promotional language in the title ("best seller," "sale," "free shipping"), repeated keywords, symbols or emoji, and internal SKUs as the leading element. Put SKU in its own attribute field so search can index it separately.

Descriptions: 500+ characters, scannable, spec-forward

  • Layout: a short opening paragraph on what the product is and who it's for; then bulleted specs; then use cases; then care and repair. Bullets and short paragraphs matter twice over: they scan on mobile, and they give the search index discrete, matchable phrases.
  • What outdoor and workwear shoppers need:
  • Materials and construction: fabric type and weight (e.g. "12 oz duck canvas"), lining, hardware, seam construction, waterproof rating (mm) and breathability where applicable
  • Weight and dimensions: packed weight for shells and packs, capacity in liters, dimensions for bags, thermos volume and hot/cold retention hours
  • Fit and sizing: true to size or not, room for layering, inseam and rise for pants, last shape for footwear, a size chart
  • Conditions and use cases: temperature range, wet vs. dry, trail vs. jobsite, which layers it pairs with
  • Durability and abrasion details: reinforced knees, bar-tacked stress points, replaceable hardware
  • Care and repair: wash instructions, re-waxing or re-proofing schedule, and what Northwind will repair. "Built to be repaired, not replaced" is the brand promise; the product page should say how.
  • Safety ratings where relevant: reflective elements, ANSI/ISEA visibility class on workwear, ASTM ratings on footwear, headlamp lumens and battery life
  • For the wholesale channel: bulk sizing availability, embroidery or customization options, minimum order quantities
  • Visual support: embed size charts, layering guides, pack-loading diagrams, and repair guides in the description field where they help. They lift conversion and cut support tickets.

Compliance: what to keep out

  • No unverified performance claims. "Waterproof," "fire-resistant," "safety-rated," and visibility class claims only when backed by a test standard or rating, cited by name. This matters more once the enterprise channel opens: commercial buyers may rely on those claims for worker safety and will hold Northwind to them.
  • No absolute superlatives ("the toughest jacket made," "guaranteed to last a lifetime") unless there's a stated warranty behind them.
  • No external links, social handles, or unrelated cross-promotion inside the description body; they dilute relevance and pull shoppers off the page.
  • Keep shipping, returns, and repair-program policy in their own site sections and link to them, rather than repeating them in product text.

How to run it

  • Prioritize by traffic: enrich the products with the most page views and the most search-driven arrivals first. With a twelve-product catalog this is a two-week content effort, not a quarter.
  • Build a description template per collection (Outdoor, Workwear, Accessories, Footwear) so structured attributes are consistent across products.
  • Store structured attributes (material, weight, capacity, waterproof rating, fit, safety class) in Shopify metafields, not only in the description body, so search, filters, and the future mobile client can all read them.
  • Write a distinct meta description for each product rather than reusing the on-page copy, so search-engine snippets do their own work.
  • Measure with the search instrumentation in item 7: zero-result query rate and search → add-to-cart rate before and after the content lands.

Risk if not addressed

  • Search abandonment stays the largest driver of lost carts. A shopper who types "rain gear" or misspells "thermos" gets an empty page today and will tomorrow. No amount of traffic growth fixes a search that only matches exact title substrings.
  • Every discovery feature adds cost. Faceted filters, related products, personalized sorting: each built on uncached routes becomes another line on the bill and another route that can throttle at peak.
  • CLS becomes a mobile problem twice over. It's worse on small screens, and Google factors it into ranking.

2.5 Commitment 4: Launch a mobile client by mid-yearNot ready

Status: Not ready. The API layer mobile would build on is the least efficient part of the platform.

What we observed

No mobile work has started, which is the good news: the decisions that determine whether mobile is cheap or expensive to run haven't been made yet. A mobile client will consume the same catalog through the same API routes the web storefront uses today. Those routes currently:

  • Return product data via RSC with x-vercel-cache: MISS, so every mobile catalog request becomes a function invocation.
  • Have no Cache-Control policy on /api/recommendations and (to verify) other /api/* routes.
  • Produce ~490 KB per product page request on web; a mobile client pulling similar payloads over cellular is slow and expensive.
  • Serve images at 1920px where 400px is needed. On mobile the transform cost, the transfer cost, and the render delay all compound.
  • Sit on a catalog with ~90-character descriptions, which on a phone means a product screen that is mostly empty space.

Why it's happening

Nothing is wrong yet; the risk is inheritance. If mobile starts before the caching, payload, and image work is done, it will be built against today's contract and will lock in today's per-request cost at roughly double the volume.

What we recommend

  1. Do the §2.2 platform work first. Mobile should start against APIs that already have cache headers, trimmed payloads, and correctly sized images.
  2. Define a mobile API contract before writing the client: which routes, what Cache-Control each returns, maximum payload size per endpoint, image size variants. Treat /api/* as a product with an SLA, not an internal detail.
  3. Prefer edge-cached reads for the catalog. Product and collection reads should be served from the CDN with s-maxage; only cart, account, and checkout should hit origin per request.
  4. Serve images through Vercel Image Optimization with mobile-appropriate widths declared explicitly, so the mobile client never requests a desktop rendition.
  5. Finish catalog enrichment (§2.4, Catalog content strategy) before mobile UX design, so the product screen is designed around real content and the structured attributes in metafields are available to the mobile client from day one.
  6. Extend the security work (§2.3) to the mobile boundary: token storage on device, certificate pinning decisions, and the same rate limiting on /api/*.

Risk if not addressed

  • Mobile doubles the function bill on day one by adding a second client to uncached routes.
  • A slow first release. Near-500 KB payloads and 1920px images on cellular produce a mobile experience that underperforms the web store it was meant to extend.
  • Two clients, one un-fixed problem. Every cost or security remediation done after mobile ships has to be done twice.
